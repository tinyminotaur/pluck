# Pluck should sell tactile context actions first

Pluck's strongest application is a content-aware four-direction launcher whose physics make the gesture feel good enough to repeat. The fidget toy is the hook and the retention loop, but it is not the pitch. The most delightful and defensible uses are, in order: (1) stable-role context actions on whatever is under the pointer (Keep N, Go E, Give S, Ask W), (2) stretch distance as a visible, risk-scaled commitment, (3) a window "throw" that snaps to the projected landing zone, and (4) a silent, meeting-safe fidget mode. Three things limit the plan. First, nothing here has been tested with users, and the research has no usage statistics for any context action, so the slot catalogs are judgment anchored on PopClip, Alfred and Raycast defaults. Second, Pluck's Accessibility dependency (plus its optional private MultitouchSupport trigger) points to Developer ID distribution, not the Mac App Store, with Setapp as a possible second channel. Third, "Pluck" collides with a same-niche macOS GitHub utility and with prior trademark filings, so clearance should come before any marketing spend. The fidget research is weak and leans negative on attention benefits, so health or ADHD claims should be avoided entirely. The ranked list of ideas is at the end.

**Evidence convention.** Claims with a link come from the research notes' fetched pages or search snippets. Many pages failed to load and most findings are search-snippet summaries, so "sourced" means "reported by a source", not "independently verified". Claims marked *(inference)* are design judgment, not fact. Repo facts come from the files in `/home/user/pluck` and are marked *(repo)*.

## Stable roles, changing verbs: the four slots per context

The one finding with real research behind it is that learnability comes from consistency. Marking-menu studies show users start by waiting for the menu and graduate to blind strokes, that the two modes are the same interaction, and that in one field case study marks averaged **3.5x faster** than menu selection, though experts still return to the menu to refresh their memory ([Buxton](https://billbuxton.com/MMUserLearn.html), [Autodesk Research](https://research.autodesk.com/publications/user-learning-and-performance-with-marking-menus)). Caveats: that study had only two users (per the notes' summary of [Buxton](https://billbuxton.com/MMUserLearn.html)), and no study tests four context-varying slots specifically. Pluck's fixed N/E/S/W with labels that appear on dwell and are suppressed on fast flicks already implements this *(repo: HANDOFF.md)*. The repo's role names (keep, go, give, ask in `PluckCore/Compass.swift`) give the rule *(inference)*: N always retains something, E always advances or opens, S always sends outward, W always asks or looks up. Only the verb changes by context, so users memorise four roles, not forty commands. If a context has fewer than four useful actions, the unused slot should stay empty and dimmed instead of duplicating another, which protects spatial memory and avoids accidental triggers *(inference)*.

The proposed catalog below is explicitly judgment. It is anchored on what PopClip ships (Cut/Copy/Paste, Dictionary, Reveal in Finder, Spelling, shown only when relevant to the selection) ([PopClip guide](https://www.popclip.app/guide/actions)), Alfred's type-filtered Universal Actions ([Alfred help](https://www.alfredapp.com/help/features/universal-actions/)), and Raycast's AI commands on a selection ([Raycast manual](https://manual.raycast.com/ai/ai-commands)). The notes found no source ranking actions by usage, so frequency ordering is my estimate. The rows for window chrome, terminal and code editor are the least grounded.

| Context | N Keep | E Go | S Give | W Ask |
|---|---|---|---|---|
| Selected text | Copy (alt: append to note) | Search, or open if URL/path | Share sheet | Look up; long-pull variant translate or AI |
| Link | Copy URL or save to reading list | Open | Share / copy as Markdown | Summarize with AI, or Quick Look |
| File/folder | Copy / tag | Open (alt: Reveal) | Share / AirDrop | Quick Look / Get Info |
| Image | Copy image | Open in Preview | Share / Save | Live Text, ask AI |
| Clipboard (empty area) | Save to snippet | Paste (plain-text variant) | Share clipboard | Ask AI about clipboard |
| Window | Pin / save layout | Snap or move to display | Send away (see throw section) | Window info |
| Email/Slack message | Save to task app | Open original | Forward / reply | Summarize / draft with AI |

The shipped defaults already match the text row: Copy, Search, Share, Look Up *(repo: `ContextResolver.textContext`)*. Three details in the current code are worth fixing. The window context uses Fill N, Right E, Bottom S, Left W, which breaks the "Go" and "Give" roles that the other contexts follow, and a window is a natural place to spend the throw idea instead of four fixed verbs. The image context drops its W slot when no file URL is known (the code simply omits the fourth item). The clipboard context fills all four slots with recent clips, which is a different mental model (a history picker) from the semantic roles *(inference: may be fine as a deliberate exception, but it should be tested)*. Also, `ActionRunner` already runs real actions *(repo)*, while HANDOFF.md says Feel Lab mode disables them; I did not verify which gate applies in the current tree.

User-defined actions should be one data model rather than a scripting escape hatch *(inference)*: a slot is {context filter, label, icon, executor, template} with variables such as `{selection}`, `{url}`, `{path}`, `{app}`, layered app-specific over context-type over global. Executors would be Shortcuts, shell or AppleScript, URL schemes, and AI prompt templates, mirroring Raycast's `{selection}` prompt commands ([Raycast manual](https://manual.raycast.com/ai/ai-commands)). One reported constraint: `shortcuts run` takes file input via `-i`, and text input needed a here-string in a 2022 report that the notes could not confirm on current macOS; shortcuts that prompt hang the CLI ([Six Colors](https://sixcolors.com/post/2022/01/shortcuts-applescript-terminal-working-around-automation-roadblocks/)). The Things, Todoist, Obsidian and Claude URL-scheme syntax was not verified in the notes and must be checked before shipping presets.

## Stretch distance, tension and release velocity are three different jobs

Well-sourced prior art for "drag distance equals value" is thin. What the notes did retrieve points one way: keep each physical channel to a single job. Figma's Option-drag scrubbing needs a speed or precision modifier, and users complain it is unreliable and its hover targets are narrow ([Figma forum](https://forum.figma.com/questions/25774), [Figma forum](https://forum.figma.com/report-a-problem-6/option-drag-alt-drag-not-working-in-all-number-fields-37280)). Pressure-widget research reports that people can discriminate only about **six** discrete levels, and only with visual feedback (a press summary of [Ramos et al., CHI 2004](https://www.dgp.toronto.edu/~bonzo/docs/p1375-ramos.pdf), via [Varsity](https://thevarsity.ca/2004/09/23/succeeding-under-pressure/); secondary source). Pull-to-refresh, invented by Loren Brichter in Tweetie, is the canonical case of folding a command into a physical pull ([MacStories](https://www.macstories.net/news/loren-brichter-talks-about-pull-to-refresh-patent-and-design-process/)). Apple's haptic API exposes exactly the two patterns Pluck needs, `alignment` for snaps and `levelChange` for stepped values, with guidance to pair them with visuals and use them sparingly ([Apple docs](https://developer.apple.com/documentation/appkit/nshapticfeedbackmanager/feedbackpattern.md)). The repo's `Haptics.tick` defaults to `.alignment` and rate-limits to 25 Hz *(repo)*.

From that, the mapping I recommend *(inference)* is: direction chooses the action; stretch distance chooses how much or whether to commit; release velocity is used only for the throw. Mixing all three on one drag makes the gesture unlearnable. Distance as commitment is the safest analog use. A three-zone stretch (dead zone, then a preview zone that shows a ghost of the result, then a visible threshold where the blob visibly "arms") lets novices see and experts flick past. Release inside the preview zone cancels with a snap-back. Thresholds scale with risk, so moving a file demands more tension than copying text, and tension itself communicates weight. No HCI study of elastic distance as a confirm gesture was found, and the notes could not cite an optimal threshold; this needs user testing. Detented stretch with three to five notches (undo depth, paste-history index, priority) fits the six-level evidence if the notches are drawn on the tether; the repo already ticks every ~56 pt *(repo)*. Continuous scrubbing (volume, zoom) is best done as rate control, where stretch sets speed and the spring-back supplies the neutral point, because fine absolute control needs a precision modifier as the Figma examples show *(inference)*. A caution: recent commits removed the tether length cap ("reach anywhere on screen", commit 85c501c *(repo)*), so the notes' premise of a bounded absolute range no longer holds, and absolute mappings would need their own scale.

## Throwing windows works with public APIs, but not across Spaces

Moving and resizing other apps' windows through the Accessibility API is mainstream: Rectangle supports macOS 14+ with AXUIElement, and its README says it cannot move windows between desktops because "Apple never released a public API for doing this" ([Rectangle README](https://github.com/rxhanson/Rectangle)). Tools that do cross Spaces rely on private APIs or, in yabai's case, partially disabling SIP ([yabai wiki](https://github.com/koekeishiya/yabai/wiki/Disabling-System-Integrity-Protection)); Hammerspoon's `hs.spaces` warns Apple can break its private-API approach at any time ([Hammerspoon docs](https://www.hammerspoon.org/docs/hs.spaces.html)). Full-screen windows are a separate Space and tilers generally cannot move them ([Rectangle issue #51](https://github.com/rxhanson/rectangle/issues/51)). Practical AX quirks reported: a position write can report success while the app ignores it, so read the frame back; `AXEnhancedUserInterface` can break positioning; and Electron apps can stutter on AX resize ([Electron PR #7206](https://github.com/electron/electron/pull/7206), [Apple forums](https://developer.apple.com/forums/thread/659755)).

The design that follows *(inference)*: on a window, the latched direction picks the destination class and release velocity picks the specific zone by projecting where the throw would land, then snapping to the nearest target. A secondary source attributed to WWDC18 "Designing Fluid Interfaces" describes this as exponential-decay projection with a deceleration rate of about 0.998, snapping to the nearest target, and passing release velocity as the spring's initial velocity ([mirror](https://mcpservers.org/agent-skills/emilkowalski/apple-design)); the notes could not verify those constants against Apple's sample code, so treat them as a starting point to tune. A short hard flick then throws as far as a long slow pull, which is the physical delight. The preview should be a drawn outline of the target frame inside Pluck's own overlay, not a window thumbnail: real thumbnails need ScreenCaptureKit and Screen Recording permission, which on macOS Sequoia re-prompts roughly monthly ([TidBITS](https://tidbits.com/2024/08/19/apple-reduces-excessive-sequoia-permission-requests-shifts-to-monthly)). Differentiation from Magnet and Rectangle (both snap on drag-to-edge or shortcut) would be that Pluck works from anywhere in the window with a visible preview and a commit threshold; this is a positioning claim, untested. The current implementation is a good start but has three issues I saw in the code *(repo: `ActionRunner.runWindow`)*: it positions the app's first AX window (`windows.first`) rather than the window under the pointer, uses `NSScreen.main` rather than the display under the pointer, and does no frame readback or full-screen check. Multi-display flipping already caused one y-axis bug in this repo, and the AX origin conversion in the code carries a leftover uncertain comment.

## Fidget, wellbeing, creative and accessibility uses need modest claims

The fidget evidence argues against positioning Pluck as a focus aid. A 2023 narrative review (Kriescher et al.) reported no evidence that fidget toys improve attention or behavior, with possible negative effects; a 2022 review found some emotional-regulation benefit but concluded classroom downsides outweigh it (both as summarized by the notes via [INSPED](https://www.insped.org.au/wp-content/uploads/2024/11/fidget-toys.pdf) and [PopSci](https://www.popsci.com/science/does-fidgeting-help-focus/), with imprecise attribution to each page; verify before quoting). One study found about an **11%** memory impairment in college students using spinners, with the author cautioning it does not apply to everyone ([PopSci](https://www.popsci.com/science/does-fidgeting-help-focus/)). Doodling and fidget products did not improve memory in Amico and Schaefer's results ([BPS summary](https://bps.org.uk/impact-small-motor-activity-attention-and-learning-children)). A countervailing finding is that more movement accompanied better working-memory performance in boys with ADHD, with a caution that only minor at-desk movement qualifies ([FSU PDF](https://www.psy.fsu.edu/clc/Publications/CLC_Sarver2015.pdf)), but it is a small study. No study of on-screen or cursor fidgeting exists in the notes. The defensible copy is "a calm thing to do with your cursor", with no focus, anxiety or ADHD claims and a note that it is not a medical product *(inference)*. A reasonable hypothesis, untested, is that a captivating visual competes for attention and a quiet peripheral one is neutral.

Within that frame, the notes' design opinions *(inference)* are sound and mostly already built: silent by default, a head that tracks the cursor with zero lag while all slosh lives in the body, idle breathing, a satisfying rebound, and instant re-grab *(repo: FIDGET.md)*. For meetings, `NSWindow.sharingType = .none` is an unreliable hint: ScreenCaptureKit and full-screen cases can bypass it, and Zoom showed flicker with it set ([Apple forums](https://developer.apple.com/forums/thread/808016), [Apple forums](https://developer.apple.com/forums/thread/69290), [Zoom community](https://community.zoom.com/meetings-2/flickering-window-in-the-screen-capture-of-zoom-mac-desktop-client-when-nswindowsharingnone-is-set-35876)). Electron's fix excludes matching windows via `SCContentFilter` ([Electron commit mirror](https://ayakael.net/mirrors/electron/commit/fd88908457a986f06e310e80499e4b2775d8ba70)). A reliable "pause when sharing" detector was not found, so Meeting Mode should stay manual and conservative (smaller, dimmer, no labels, auto-cancel) with the repo's existing 65% size and 80% opacity as a starting point.

A paced-breathing mode (hold the blob and let it swell and subside) is plausible. The sourced base is modest: slow-paced breathing near six cycles per minute shows short-term cardiovascular improvement and a modest reduction in negative emotion, with long-term effects unestablished ([Springer, Mindfulness 2023](https://link.springer.com/article/10.1007/s12671-023-02294-2)), and a micro-break meta-analysis found small gains in vigor (d=.36) and fatigue (d=.35) but no significant performance gain (d=.16) ([DOAJ](https://doaj.org/article/c6f37b6ba159469296b2cb968b65505f)). Note that the anxiety and stress effect sizes the notes list come from a secondary summary ([Simply Psychology](https://www.simplypsychology.org/?p=72165)); I omit them. No safety guidance for breathing exercises was retrieved, so the mode should carry only "paced breathing guide" wording and no streak guilt. Creative uses (a presenter cursor-finder, an ink or color picker driven by stretch and direction, an opt-in pitch toy) had no sources at all and are speculative *(inference)*; the presenter and teacher highlight use is the most plausible because the gesture is visible on camera and it requires the opposite of the meeting-mode capture exclusion.

Accessibility is both an obligation and an opening. The gesture is a drag, and WCAG 2.2 criterion 2.5.7 requires a single-pointer alternative to dragging; 2.5.8 sets a 24x24 CSS px minimum target; flashing above three per second fails 2.3.1 ([W3C What's New in WCAG 2.2](https://w3.org/WAI/standards-guidelines/wcag/new-in-22/), [Webflow checklist](https://webflow.com/accessibility/checklist/task/use-subtle-animations-that-dont-flash-more-than-recommended)). WCAG formally covers web content, so for a native app these are benchmarks, not legal requirements. macOS exposes Reduce Motion, Reduce Transparency and Increase Contrast preferences ([Apple Support](https://support.apple.com/guide/mac-help/change-display-preferences-for-accessibility-unac089/12.0/mac/12.0)); the repo reads Reduce Motion but, per HANDOFF.md, does not yet handle Reduce Transparency or Increase Contrast *(repo)*. Recommended *(inference)*: a sticky click-to-toggle mode and a keyboard-hold trigger, a dwell-to-summon option, hysteresis and large dead zones (the repo already has 24/16 pt hysteresis), VoiceOver announcement of the highlighted action, and solid edges instead of glints under Increase Contrast. The notes did not verify WCAG 2.5.1, macOS Dwell Control, or Apple HIG text, and no research covers vestibular risk from small on-screen motion, so claims to disabled users should wait for testing.

## Prior art leaves content-under-pointer plus physicality unclaimed

The category is real but small. Radial (a pie menu at the cursor with app-aware macros) had a Product Hunt launch with 94 upvotes, and its developer said sub-menus and a menu switcher were the most requested follow-ups ([Product Hunt](https://www.producthunt.com/p/radial)). Pie Menu shows the active app's shortcuts and uses a 10-uses-per-day free tier ([hunted.space](https://hunted.space/product/pie-menu)). Kando is free and open source with **6.4k** GitHub stars, per-app menus and donation funding ([GitHub](https://github.com/kando-menu/kando)). Logitech's Actions Ring offers 8 bubbles plus 9 sub-bubbles, haptic feedback on the trigger, and depends on a plugin service whose failure has its own support article ([Logitech support](https://support.logi.com/hc/sv/articles/17859365804439-What-is-the-Actions-Ring-feature-in-Logi-Options), [Logitech troubleshooting](https://support.logi.com/hc/vi/articles/18118701623959-Actions-Ring-icon-does-not-show-up-has-disappeared-from-Logi-Options-Home-screen)). One reviewer called the ring's haptics pleasant but closer to novelty than productivity, and Logitech's "33% time saved" figure is a vendor claim from a 37-user internal study ([Tbreak](https://tbreak.com/logitech-mx-master-4-uae-haptics-actions-ring/), [Business Wire](https://www.businesswire.com/news/home/20250930356623/en)). A Galaxus reviewer simply prefers keyboard shortcuts ([Galaxus](https://www.galaxus.at/en/page/logitech-mx-master-4-tested-genius-mouse-with-one-frustrating-flaw-39723)). PopClip is the closest functional relative (selection-based actions, an installable extension format), and BetterTouchTool covers trackpad gestures ([BTT docs](https://docs.folivora.ai/docs/601_magic_mouse_trackpad.html)).

What makes these delightful or annoying, per the evidence, is thin and mostly inferred. Delight signals: haptics on trigger, per-app menus, shareable macro presets, and zero-configuration defaults. Annoyances that are documented: hardware gating and a fragile background service (Logitech), narrow or unreliable gesture affordances (Figma scrub), and extension permission sprawl (PopClip extensions request extra permissions, per [PCWeenies](https://pcweenies.com/?p=9212)). Accidental triggers on a high-traffic button are a plausible risk with no retrieved user reports. The gap Pluck can fill is that Radial and Pie Menu key off the frontmost app, not the object under the pointer, and PopClip does selection only with no radial UI. This comes from limited descriptions, and the notes did not research Hammerspoon, Dropzone, Contexts, Jitouch, StrokesPlus or others, so a hands-on teardown should precede any "first" claim. Kando in particular is the nearest UX relative, and Pluck's differentiator is physicality plus content-awareness, not the radial idea.

## Positioning, trust, price and distribution

**Positioning.** Lead with a short looping clip of stretch-and-release, with the headline being productivity ("four context actions under your pointer") and delight as the proof. A macOS menubar developer who added a demo video moved a Product Hunt launch from 10 upvotes to #3 and nearly doubled downloads, and another reported that lacking a trial hurt conversion (single-developer anecdotes: [Hackernoon](https://hackernoon.com/lite/i-turned-a-failed-product-hunt-launch-into-a-top-3-win-on-a-budget), [Indie Hackers](https://www.indiehackers.com/post/results-lessons-learned-from-my-first-product-hunt-launch-dbf1641187)). Segment order by fit *(inference)*: launcher and Mac power users, designers, educators and streamers (the visible gesture reads on camera), then fidgeters, without medical claims.

**Onboarding and discoverability.** Kurtenbach's principles of self-revelation, guidance and rehearsal map directly to Pluck: a stretch-and-hold reveals labels, fast flicks skip them ([Buxton](https://billbuxton.com/MMUserLearn.html)). Proposed first-run *(inference)*: a practice blob with a fake target needing no permission, then one real action on a harmless sample, and only then the Accessibility request, so the grant follows a moment of delight. Fade each direction's labels as its use count rises. The proposed success metrics (first real action in session one, three or more actions per day at seven days) are my proposals, not sourced.

**Trust and the permission.** Apple tells users to grant Accessibility only to apps they trust ([Apple Mac User Guide](https://support.apple.com/guide/mac-help/mh43185/)). Vendor guidance is to explain before the system alert, deep-link to Privacy & Security, and handle stale entries ([Irradiated Software](https://www.irradiatedsoftware.com/help/accessibility/)). PopClip's developer argued that user-granted permissions already protect Accessibility ([Michael Tsai](https://mjtsai.com/blog/2024/03/21/popclip-leaving-the-mac-app-store/)). Pluck's trust levers *(inference)*: open source (the repo is Apache-2.0 per the notes), signed and notarized, no network code with a verifiable statement, and an in-app "what we read, what we never do" panel. Two honesty points: the listen-only, never-synthesize-input claim is credible because HANDOFF.md states it as a design rule, but actions that use AppleScript (Finder Get Info, and Finder selection reading in `ContextResolver`) trigger per-app Automation prompts and must be disclosed *(repo)*. Also avoid Screen Recording, the one permission with documented recurring re-prompts, and which TCC pane Pluck's NSEvent global monitors trigger on macOS 14 to 26 was not established in the notes.

**Distribution.** Apple's own engineers disagree on whether Accessibility works in the sandbox: one said sandboxing does not prohibit it, a later one said the APIs are not supported in sandboxed apps ([Forums 756130](https://developer.apple.com/forums/thread/756130), [Forums 836644](https://developer.apple.com/forums/thread/836644), [Forums 810677](https://developer.apple.com/forums/thread/810677)). A window-manager developer reported AX writes failing in the sandbox even with permission granted ([Forums 836644](https://developer.apple.com/forums/thread/836644)). PopClip left the Mac App Store in March 2024 over sandbox rules and now sells directly and via Setapp ([Michael Tsai](https://mjtsai.com/blog/2024/03/21/popclip-leaving-the-mac-app-store/), via a search summary since the page fetch failed). A blogger claims a tiler reached the store by delegating window moves to Shortcuts, which is an unconfirmed author claim ([Blake Crosley](https://blakecrosley.com/blog/window-manager-mac-app-store-sandbox)). On the private API: Pluck loads MultitouchSupport via `dlsym` *(repo)*, and non-public API use is cited under App Review guideline 2.5, with rejections that can name the symbol or framework, including from bundled third-party code ([Forums 740163](https://developer.apple.com/forums/thread/740163)). No documented MultitouchSupport-specific rejection was found. My conclusion *(inference)*: ship Developer ID with notarization and Sparkle as primary; keep the three-finger trigger optional, behind a build flag and runtime load so it degrades gracefully when macOS changes the framework; consider Setapp as secondary. A reduced Mac App Store build would lose most of the product's value.

**Pricing.** The category norm is a low one-time price: Magnet **$4.99** ([MacStories](https://www.macstories.net/?p=48075)), Yoink **$8.99** ([Eternal Storms](https://blog.eternalstorms.at/2025/11/03/yoink-for-mac-v3-6-104-now-available-also-as-direct-purchase/)), Keyboard Maestro **US$36** ([wiki](https://wiki.keyboardmaestro.com/manual/Purchase)). Other figures conflict or are unverified and should not be quoted: PopClip is reported variously at about $14.99, $17 or EUR 20 with 100 to 250 trial uses ([Macworld](https://www.macworld.com/article/706796/popclip-review.html), [AlternativeTo](https://alternativeto.net/software/popclip/about)); BetterTouchTool at $9/$21 or $12/$24 depending on source; Radial's $15 and Raycast Pro's $8 to $10 per month come from aggregator listings. A one-time license in roughly the **$10 to $25** band with a free trial and an optional free open-source core is my inference from that band, supported only by the low-price pattern. Subscription pricing would be out of pattern for a utility without cloud or AI value. A skins and action-pack marketplace is a plausible lever but no ecosystem revenue evidence was found.

**The name.** Pluck, Inc. filed trademark applications for mobile apps (serials 86947014 and 86947017); an earlier PLUCK registration for content-aggregation software was cancelled in 2017 ([Justia](https://trademark.justia.com/owners/pluck-inc-3276371), [Justia 78814213](https://trademarks.justia.com/788/14/pluck-78814213.html)). More pressing, a GitHub project `advegaf/pluck` is a macOS utility that copies selected text on press-and-hold, in the same niche ([gitblind mirror](https://gitblind.noratr.app/advegaf/pluck)). Live USPTO status was not retrieved, and this is not legal advice. Run a Class 9 and 42 clearance search plus app-store, domain and handle checks first, and treat renaming as a live option while the name is still cheap to change.

## Ranked application ideas with sketches and feasibility

Ranking weighs delight, trust, differentiation and effort *(inference throughout)*. "Repo" notes reflect a brief reading of `ActionRunner`, `ContextResolver`, `Compass`, `Haptics` and the commit log, not a line-by-line audit.

| # | Idea | UX sketch | Feasibility in this repo |
|---|---|---|---|
| 1 | **Real context actions with stable roles** (text, link, file, image, clipboard) | Grab selected text, pull toward Copy N, Search E, Share S, Look Up W; labels on dwell, none on flick | Largely built: `ContextResolver` plus `ActionRunner` exist *(repo)*. Work: confirm Feel Lab gating, fix empty-slot and clipboard-role oddities, add plain-text paste. Low |
| 2 | **Two-zone stretch: preview, then armed commit, with risk-scaled thresholds** | Short pull previews the result in the pill; past a ring the blob crystallizes and arms; releasing before it snaps back to cancel | Cheap: distance, hysteresis, cancel ring, armed pop and commit flash exist *(repo)*. Needs a per-action risk level and threshold tuning. Low to medium |
| 3 | **Window throw-snap** | Grab a window anywhere; flick toward an edge; an outline ghost shows the projected zone (halves, quarters, maximize, next display); release to snap | Medium. `runWindow` exists but must target the window under the pointer and the pointer's display, read back frames, handle min size and full-screen, and draw the ghost in the overlay. Skip Spaces |
| 4 | **Silent fidget and Meeting Mode** (the retention loop) | Always-alive blob, snap-back thwip, idle breathing, trackpad ticks, dim and small on demand | Mostly built *(repo: FIDGET.md)*. Add auto-cancel and per-app exclusion UI (an `ExcludeList` exists in PluckCore *(repo)*); verify the rendering path's CPU/battery cost (known readback issue). Low |
| 5 | **Onboarding sandbox: practice blob before the permission ask** | Fake target in the setup window; success triggers the Accessibility request with a deep link | Medium: `SetupView` and `Permissions` exist *(repo)*; needs a no-permission demo mode and grant auto-detection |
| 6 | **Detented stretch for stepped values** (paste-history depth, undo depth, priority) | Notches with numbers along the tether, tick per notch | Cheap; reuse ~56 pt ticks, add `.levelChange` and drawn notch marks. Verify mouse users get visual-only feedback |
| 7 | **Accessibility alternatives** (sticky toggle, dwell, keyboard hold, Reduce Transparency and Contrast) | Click once to summon, pick with arrows or pointer, Esc cancels | Medium; HoldArm and modifier triggers exist *(repo)*; the rest is new work and needs testing with disabled users |
| 8 | **User-defined slots** (Shortcuts, URL scheme, AI prompt) | Per-context, per-app overrides in a small editor, with importable packs | Medium to high: new model, editor and sandbox-free executors; verify URL-scheme and Shortcuts input behavior first |
| 9 | **Rate-control scrub** (volume, zoom) with spring-return neutral | Hold stretch to ramp; release snaps to neutral | Cheap to medium; needs system-volume APIs and a precision mode |
| 10 | **Presenter and educator cursor mode** | Visible blob as a highlighter on camera, capture-inclusion toggle | Low to medium; speculative demand, no sources |
| 11 | **Paced-breathing mode** | Swell and subside at a slow pace while held | Low effort, weak value; only with "guide" wording and no claims |
| 12 | **File flick to configured folders, with undo** | Pull a file toward a destination; a long pull commits; toast offers undo | Medium; FileManager moves plus an undo stack. High trust risk if wrong |
| Defer | Throw across Spaces; live window thumbnails | | High risk: private APIs or SIP changes; Screen Recording and monthly re-prompts |

Two cross-cutting risks affect everything above. The HANDOFF.md states that interactive feel, haptics, cursor hiding and the trackpad triggers have not been verified on a real Mac, and that the trackpad hold trigger is listen-only so the underlying app also receives the click, which may conflict with window dragging and Finder drags. Idea 3 and any trackpad-first positioning depend on resolving that.

## Conclusion

The research reframes Pluck's choice: the physics are not an alternative to utility but the reason to adopt a small, otherwise ordinary four-slot launcher. The evidence supporting actual productivity (marking menus) is stronger than the evidence supporting wellbeing (weak, leaning negative for attention), so the product should earn its place with reliable actions and let the fidget quality bring people back. The most under-explored asset is the commit threshold: tension as a visible price for risky actions is a novel use of the metaphor, and nothing in the notes contradicts it, but nothing tests it either.

Three questions will decide the roadmap. Does a user reach for the gesture unprompted on day seven? Is the trackpad trigger acceptable given the pass-through click? And can the name survive clearance? The first two need a real Mac and real users, and the third needs a trademark search. The notes' large gaps (no usage data, no hands-on competitor teardown, no verified prices, no health-claim support) argue for a small private beta before any launch.
