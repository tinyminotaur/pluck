# Tuning Pluck's obsidian blob: sourced rules versus recalled craft

The best-supported design decisions for Pluck are already in the repo: **four radial directions, 90-degree slices, a 24/16 pt hysteresis pair and a smooth-min SDF union** all sit in the low-error regime the literature describes. The highest-value changes are mostly engineering rather than aesthetic. First, replace the `waitUntilCompleted` plus CPU readback plus `CGImage` path in `ObsidianBlobMetal.swift` with a `CAMetalLayer` presented directly. Second, move the physics onto a fixed-timestep accumulator with a velocity clamp. Third, gate the label bloom so fast flicks never flash labels. Fourth, add dithering, Reduce Transparency and Increase Contrast handling to the shader. Almost all of the numeric "feel" targets (liquid versus jelly damping, facet snapping, necking curves, commit and cancel timings) are **recalled craft or opinion, not sourced findings**. They should be treated as starting values to tune by eye. The research notes found no citable source for obsidian-specific UI motion, for liquid-versus-jelly spring bands, or for dead-zone pixel values. This report labels each claim as [SOURCED] or [RECALLED/OPINION] and lists the gaps. It ends with a prioritized change list keyed to files and parameter values.

## What the sources support, and where they stop

The sourced material is thin but solid at the architectural level. On gesture UX, Callahan et al. (CHI '88) found pie menus faster and less error-prone than linear menus because direction selection has a fixed distance and large targets (the roughly 15% figure is secondhand) ([UMD abstract](https://sites.umiacs.umd.edu/node/16962)). Kurtenbach and Buxton found that keeping errors under 10% allows **breadth 4 at up to 4 levels deep, versus only 2 levels at breadth 8** ([Autodesk Research](https://www-pt.autodesk.com/research/publications/the-limits-of-expert)). Zhao, Agrawala and Hinckley report accuracy dropping substantially beyond breadth 8 ([CHI 2006](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/11/Zone-Polygon-Menus-CHI-2006.pdf)). Pluck's four 90-degree slices are therefore not where errors will come from; dead-zone, hysteresis and overshoot handling will be. The classic marking-menu delay is about 330 ms before the menu appears, so experts can mark ahead ([Autodesk](https://www-int.autodesk.com/research/publications/an-empirical-evaluation-of)). Henderson and Lank found no obvious systematic advantage for delay-and-mark mode, with only a ~260 ms benefit after significant training and with two items ([HAL](https://hal.archives-ouvertes.fr/hal-02463247)). That makes a short gate defensible but not mandatory. Blender's pie menu supplies the closest precedent for Pluck's press-drag-release shape: a direction is valid only after leaving a centre disc, and positions are fixed ([Blender wiki](https://wiki.blender.org/index.php/User:Psy-Fi/Pie_Menus_Manual)). Its known bug, where an edge-clamped menu auto-validated the edge item, is a direct warning for Pluck's label placement near screen edges ([Blender T49029](https://developer.blender.org/T49029)).

On rendering, Apple documents the `CAMetalLayer` path (`nextDrawable`, render, `present`), recommends acquiring drawables late inside an `autoreleasepool`, and lists the properties that matter ([Apple: CAMetalLayer](https://developer.apple.com/documentation/quartzcore/cametallayer.md)). `CAMetalDisplayLink` exists from macOS 14 and hands the update loop a drawable with target timestamps ([Apple](https://developer.apple.com/documentation/quartzcore/cametaldisplaylink.md)). TN3133 says SwiftPM compiles `.metal` files into a metallib loaded with `makeDefaultLibrary(bundle: .module)` ([Apple TN3133](https://developer.apple.com/documentation/technotes/tn3133-packaging-a-renderer.md)). For physics, Gaffer's fixed-timestep accumulator ([Fix Your Timestep](https://gafferongames.com/post/fix_your_timestep/)) and the "Small Steps" result that many substeps with one iteration beat one step with many iterations ([EG digital library](https://diglib.eg.org/handle/10.1145/3309486-3340247)) are the two firm anchors. Shading support is weakest. The sources establish Schlick Fresnel with F0 near 0.04 and per-channel Beer-Lambert absorption ([luma.gl](https://luma.gl/docs/api-guide/shaders/glass-effects)), the Voronoi F2-F1 edge trick ([GameDev.net](https://gamedev.net/shaderlab/22-voronoi-cells/)), and interleaved gradient noise for dithering ([LYGIA IGN](https://git.gay/kaneraZh/lygia/src/branch/main/color/dither/interleavedGradientNoise.msl)). Nothing citable covers conchoidal-fracture shading, obsidian UI, or liquid-versus-jelly timing.

## The overlay pipeline is the largest sourced win

`ObsidianBlobMetal.render` currently draws to an offscreen texture, calls `cmd.waitUntilCompleted()`, copies pixels with `getBytes`, scrubs every pixel with alpha under 10, and builds a `CGImage` ([Sources/Pluck/Overlay/ObsidianBlobMetal.swift](/home/user/pluck/Sources/Pluck/Overlay/ObsidianBlobMetal.swift), lines 143-179). `MetaballRenderer` then pushes that image from a `CVDisplayLink` callback with `needsDisplay`. This blocks the CPU on the GPU every frame and adds a full readback. The CAMetalLayer path removes all of it, and it also removes the need for the "plate isolation" scrub, which exists only because `CGImage` painted translucent rectangles. The notes' recommended configuration is [SOURCED] for the API shape and [RECALLED/OPINION] for the values: `isOpaque = false`, `pixelFormat = .bgra8Unorm`, `framebufferOnly = true`, `maximumDrawableCount = 2` (use 3 if `nextDrawable` stalls), `allowsNextDrawableTimeout = true`, constant `drawableSize`, and a clear colour of (0,0,0,0). The fragment output is already premultiplied (`body * a, a`), which is the form Core Animation expects, so the shader needs no change there. The panel should be sized to the blob bounding box plus margin and moved with `setFrameOrigin`; the code already computes a padded bbox (`pad = 32`). Because SDF samples are cheap but a full Retina-5K drawable is not, keep the drawable small and constant. Run the display link only while the overlay animates.

Two caveats limit confidence. The notes could not confirm that `CAMetalDisplayLink` property names (`preferredFrameRateRange`, `preferredFrameLatency`) behave as recalled, so use a CVDisplayLink-to-main hop as the fallback if they differ. They also could not confirm that plain `swift build` runs the Metal compiler for `.metal` resources on all toolchains, so moving the shader out of the Swift string literal (currently `makeLibrary(source:)` at line 33, which compiles at every launch and fails silently to a nil renderer) should be verified on the project's CLI build before committing to it. Keep runtime source compile as the fallback.

Cursor handling carries an unsourced risk. `MetaballRenderer.tick` calls `NSCursor.hide()` every frame and `PluckSession.hideCursor` calls it four times plus `CGDisplayHideCursor`. Apple's cursor guide says the hide functions require the app to be in the foreground, and the only background route found is the undocumented `SetsCursorInBackground` property, which one forum thread says is unsupported ([Apple forums](https://developer.apple.com/forums/thread/756199)). The hide count is balanced, so the repeated calls should be paired exactly with unhides; the existing `showCursor` does call unhide four times, but over-unhiding is harmless while under-unhiding strands an invisible cursor. Add an Escape-or-timeout guarantee that restores the cursor (the 20 s auto-cancel already helps) and test on a full-screen Space.

## Physics: keep the head kinematic, fix the timestep, then tune feel

The current loop clamps `dt` to [1/240, 1/30] and integrates once per display tick with `step = dt * dt * 60`, a 60 fps-tuned scaling. Verlet with variable `dt` does not make Verlet frame-rate independent, because the `(cur - prv)` velocity term silently assumes the previous `dt` equalled the current one. On a ProMotion display that alternates frame times this produces visible changes in damping. The sourced fix is Gaffer's accumulator: step at a fixed `h` and carry the remainder ([Fix Your Timestep](https://gafferongames.com/post/fix_your_timestep/)). The notes' [RECALLED/OPINION] values are `h = 1/240 s`, an accumulator capped at about four steps, and render interpolation if the physics rate is not a display-rate multiple. The "Small Steps" paper supports preferring several small substeps to the current five constraint iterations per frame at a single large step ([EG](https://diglib.eg.org/handle/10.1145/3309486-3340247)). Concretely, run the existing spring-plus-whip-plus-distance-constraint body four times per 60 Hz frame with 2 relaxation passes each rather than once with 5.

The whip impulse is the second stability concern. `impulse = latSpeed * mid * 0.05 * whip` takes `latSpeed` from a head velocity estimated as a raw finite difference over `max(dt, 1/240)`, then smoothed with a per-frame retain of 0.55. A single coalesced mouse event can spike that estimate. The notes suggest [OPINION] a soft clamp such as `tanh` on injected speed so a 5000 px/s flick cannot blow up the chain, and an exponential velocity average with a time constant of 20-40 ms. The existing retain of 0.55 at 60 Hz corresponds to roughly a 28 ms time constant, so it is already in range once it is converted to a time constant; the missing piece is the clamp. The 1 euro filter ([Casiez et al., CHI 2012](https://hal.archives-ouvertes.fr/hal-00670496)) is the sourced option for derived signals, with the head itself left unfiltered. Pluck already follows this: the head is pinned to the pointer and all lag lives in the body.

For feel targets, the only sourced numbers are Apple's: bounce around 0.15 is barely bouncy, around 0.3 is clearly bouncy, and above about 0.4 is risky for UI ([WWDC notes snippet](https://wwdcnotes.com/notes/wwdc23/10158)). The "liquid" band the notes propose (damping ratio 0.45-0.7 for the whole-body recoil with a period of 160-260 ms, and slosh sub-oscillators at 1.5-3x frequency and zeta 0.15-0.3 that die within 400 ms) is [OPINION]. The distinguishing cue for liquid versus jelly is mass lag and a travelling lateral wave rather than oscillation count. Pluck's slosh oscillator uses a restoring rate of 16 per unit step and velocity damping of 0.9 per frame, and it adds a free-running `sin(time * 8.5 + t * 5.5)` term scaled by speed. That sine term supplies a continuous travelling wave while the pointer moves, which suits the liquid cue, but it should fade to zero when speed falls so the blob settles. Radius modulation should stay within about 8-15% of base radius (the notes say beyond about 25% reads as jelly). `rescaleToTotalArea` already conserves area after slosh is applied, which matches the notes' advice to redistribute rather than add volume.

Necking and pinch-off are only relevant if Pluck ever lets the tether break. The sourced physical anchor is the Plateau-Rayleigh limit: a weightless liquid bridge is stable up to length/diameter of pi ([arXiv 1010.2562](https://arxiv.org/pdf/1010.2562)), and viscous or stabilized columns exceed it ([MDPI](https://www.mdpi.com/2073-4352/12/8/1092)). Since the design caps stretch with a head clamp and never separates the blob from the pin, Pluck does not need pinch-off. The only cheap borrowing is the volume law, with neck radius proportional to 1/sqrt(stretch) ([RECALLED]), which `BlobMass.radiusProfile` presumably already approximates. Do not build a break-and-satellite-droplet system on the strength of the notes' 60-120 ms collapse timing; that figure is opinion.

## Shading: Pluck's model is sound; add the missing obsidian cues

The shader already contains the right sourced ingredients: a Fresnel term (`pow(1 - N.V, 2.2)`), Beer-Lambert transmission (`exp(-absorb * thick * 1.1)`), a Blinn spec, and F2-F1 Voronoi seams computed in the blob's own material space along the pin-to-head axis. That last choice matches the notes' temporal-stability advice: facets stretch with the liquid and do not shimmer in screen space. Three gaps remain.

First, **banding**. A near-black body at 8 bits will band. Add interleaved gradient noise, `fract(52.9829189 * fract(dot(p, float2(0.06711056, 0.00583715))))`, scaled to about +/- 0.5-1.0 / 255 and applied after final colour assembly, before premultiplication ([LYGIA IGN](https://git.gay/kaneraZh/lygia/src/branch/main/color/dither/interleavedGradientNoise.msl); amplitude is [OPINION]). Noise dither is preferred over Floyd-Steinberg or Bayer in animation ([kodewerx](https://blog.kodewerx.org/2017/08/3d-renderer-dithering.html)).

Second, **smoky amber rim transmission**. The recalled cue that separates obsidian from black plastic is thin edges that transmit brown-amber light while thick areas go to black. The shader's `absorb` uniform and `glow` colour already provide this; the notes suggest sigma on the order of (1.2, 2.5, 4.0) per unit thickness as a starting point ([OPINION]; no citable source for the amber behaviour). Check that the current `absorb` values are strongest in blue and weakest in red. Sheen variants (gold or rainbow) trace to oriented inclusions along flow layers, with sources disagreeing on the physical cause ([Wikipedia](https://en.wikipedia.org/wiki/Obsidian) versus [Oregon State](https://volcano.oregonstate.edu/volcanic-minerals/obsidian)); treat them as an optional low-intensity (below 0.3) spec tint across a flow-band stripe, not simulated physics.

Third, **conchoidal facets that read as curved**. The present normal tilt is a flat per-cell constant, `Nf = normalize(N.xy * 0.45 + tilt * 0.55, N.z)`, which gives a low-poly sticker look. The notes' [OPINION] fix is domed cells: add a term proportional to the offset from the cell centre, and a faint concentric ripple (tilt modulated by `sin(freq * |p - c|)` at 0.02-0.05 amplitude) to evoke hackle lines. The shader's `facetCells` does not currently return the cell centre vector, only distances and a hash pair, so this needs a small change to return the nearest seed offset. Facet motion should snap rather than shimmer: quantize the light-driven term per facet with a narrow smoothstep and a per-facet phase offset, with only 2-4 facets lit at once. Current code uses a smooth `sin(u.time * 2.0 + cell.z * 6.28)` brightness wobble of 12%, which reads as shimmer instead of glint; the notes suggest [OPINION] replacing it with a sharp half-vector threshold per cell. For performance, the three extra `pillow(blobField(...))` evaluations for finite-difference normals multiply the SDF cost by four. An analytic gradient from the same smooth-union loop (or a forward difference reusing the centre sample) cuts that, but the notes gave no Apple Silicon measurements, so profile before and after.

For accessibility, Apple's Reduce Transparency makes glass more opaque, Increase Contrast adds borders, and Reduce Motion disables elastic effects ([MobileSyrup](https://mobilesyrup.com/2025/06/10/how-apple-is-making-sure-liquid-glass-as-legible-as-possible/)). Pluck's obsidian body is already near-opaque (the notes argue this fails less over busy content than true glass), so the practical changes are a stronger rim under Increase Contrast and honouring Reduce Motion. `PluckSession` defines `reducedMotion` (line 26) but a repo search finds no other use, so it appears unwired. The `NSWorkspace` property names are from general AppKit knowledge and unverified in the notes.

## Gesture logic: keep the geometry, change the timing and the edge cases

`GestureMath` sets `deadZone = 24`, `deadZoneExit = 16`, `hysteresisAngle = 0.14` rad (about 8 degrees per side) and `armWindow = 0.040 s`. The ratio of 1.5 between arm and stay-armed distances and roughly 106-degree effective held slice are in a sensible range, but neither is backed by a sourced number; the notes found no pixel dead-zone data for mouse marking menus. The one sourced structural rule is that the centre disc must be left before a direction is valid, and that slices are unbounded radially, so an armed target must stay latched at any larger radius. Confirm that `capture` never drops a role at large radius.

Label timing is where the notes make their most actionable gesture recommendation. `PluckSession.startEmergence` uses `bloomDelay = 0.08` and `bloomDur = 0.28`, so labels begin appearing 80 ms after press regardless of what the user does. A fast expert flick therefore sees label flashes on every gesture. The sourced reference delay is about 330 ms, though Henderson and Lank weaken the case for any long mandatory delay. The notes' [RULE OF THUMB] compromise is a gate of 150-300 ms, or until pointer speed drops, before labels fully bloom, with the blob itself responding immediately. Pair this with a flick-commit rule: on release with high velocity and a stable direction, commit even if under 24 pt. That, plus arming earlier (14-16 pt) when the peak speed is high, is [RULE OF THUMB] and untested; add it behind a constant so it can be disabled.

Edge safety is the sourced anti-pattern. Hopkins advises keeping geometry identical and shifting only labels near edges ([Sugar-devel](https://lists.sugarlabs.org/archive/sugar-devel/2007-February/001614.html)); Blender's T49029 bug shows the cost of clamping the menu so the pointer starts inside an active slice. Pluck anchors on the pin so no cursor warp is needed. Keep slice logic independent of label placement and compute edge distances per `NSScreen.visibleFrame` so the menu bar and Dock are avoided. For outward-effect roles such as Give, the notes suggest an Undo toast ([RULE OF THUMB]). Release in the dead zone currently cancels, matching Blender's centre-disc behaviour; Blender's click-style fallback (release without moving keeps the picker open) conflicts with that and is not worth adopting without user testing. Haptics via `NSHapticFeedbackManager` fire only with a finger on a Force Touch trackpad, so they can only be a bonus paired with visual feedback ([Apple](https://developer.apple.com/documentation/appkit/nshapticfeedbackmanager.md)). Keyboard and VoiceOver alternatives follow Apple's non-gesture-alternative guidance, which the notes could confirm only through a secondary summary.

## Source gaps to keep in view

Several gaps affect how much weight the recommendations can bear. Primary papers (Kurtenbach and Buxton, Zhao, Lepinski) were reachable only as abstracts or secondary summaries, so the per-direction error rates and exact delay parameters are unverified. No source gives dead-zone pixel values, haptic latency, or input-latency thresholds, so the 24/16 pt values and the "under 250 ms" response target are common practice, not findings. The Apple WWDC25 Liquid Glass sessions, the Metal Best Practices Guide and the WWDC23 spring formulas were not retrieved, so the duration/bounce to damping-ratio mapping (bounce 0.3 as zeta 0.7) is recalled and must be checked against Apple documentation. Nothing was found on obsidian rendering in Shadertoy, artist breakdowns or measured reference colours, so the shading values rest on first principles. No Apple Silicon benchmarks exist for the shader. Finally, the notes could not verify that hosted macOS runners expose a Metal device, that `xcrun metal` needs a separately downloaded toolchain, or that `SetsCursorInBackground` still works on current macOS releases.

## Conclusion

The research changes the question from "how do we make the blob look more like obsidian" to "which parts of the existing design are on solid ground and which are guesswork". The pipeline and timestep fixes rest on documented APIs and published results, and they remove real defects (a per-frame GPU stall, frame-rate-dependent damping). The shape of the gesture is already inside the evidence-backed region. The appearance and feel layer, covering facet curvature, glint snapping, liquid damping bands and commit timings, has no citable foundation, so each of those should land behind a named constant and be judged by eye on real hardware.

The most useful next step is measurement: add a debug overlay for frame time and `nextDrawable` wait (via `developerHUDProperties`), then tune. The sourced findings say where to build the foundation; the opinion-grade values say only where to start looking.
